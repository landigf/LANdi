1 Quick Start

🔌 Connect to PC1

Run this in your terminal:
docker exec -it clab-frr01-PC1 sh

What this does:

Opens an interactive shell inside the PC1 container where you can run Linux networking commands.

🔍 First 5 Commands (Run Inside Container)

1. Show network interfaces:
ip a

What to look for:

• Interface name: eth0
• IP address: 10.0.1.10/16
• MAC address: link/ether
• State: UP

2. Show routing table:
ip r

What to look for:

• Default gateway: default via 10.0.0.1
• Local subnet: 10.0.0.0/16 dev eth0

3. Test connectivity to R1:
ping -c 3 10.0.0.11

What to look for:

• 3 packets transmitted, 3 received
• 0% packet loss
• RTT (round-trip time) < 1ms

4. Check ARP cache:
ip neigh

What to look for:

• Router's IP → MAC mapping
• State: REACHABLE or STALE
• This shows Layer 2 (MAC) resolution

5. Exit container:
exit

2 Scenario 1: TCP Connection Analysis

🎯 Goal: Understand TCP handshake and connections

Connect to R1 router:
docker exec -it clab-frr01-R1 bash
Install & start simple HTTP server:
apt update && apt install -y python3 && python3 -m http.server 8080 &
Check listening sockets:
ss -tuln

What you'll see:

• LISTEN on port 8080
• Socket bound to 0.0.0.0:8080 (all interfaces)
• State: LISTEN

From PC1, make HTTP request:
docker exec -it clab-frr01-PC1 wget -O- http://10.0.0.11:8080
Back in R1, check established connections:
ss -tan | grep 8080

What to analyze:

• ESTABLISHED connection from PC1
• Send-Q and Recv-Q buffers
• Local:8080 ↔ Remote:ephemeral_port

Interview Question: What happens during TCP 3-way handshake?
Answer: SYN → SYN-ACK → ACK. Client sends SYN with ISN, server responds with SYN-ACK and its ISN, client ACKs. Connection becomes ESTABLISHED.

3 Scenario 2: Packet Capture with tcpdump

📡 Goal: Capture and analyze network traffic

In R1, install tcpdump:
apt install -y tcpdump
Start packet capture (run in background):
tcpdump -i eth0 -w /tmp/capture.pcap &
Generate some traffic (from PC1):
docker exec -it clab-frr01-PC1 ping -c 5 10.0.0.11
Stop tcpdump (in R1):
killall tcpdump
Read the capture:
tcpdump -r /tmp/capture.pcap -n

What to look for:

• ICMP echo request/reply packets
• Source/destination IPs
• Packet sizes and TTL values
• Timestamps between packets

Interview Question: How would you capture only HTTP traffic?
Answer: tcpdump -i eth0 port 80 or port 443 or tcpdump -i eth0 'tcp port 80'

4 Scenario 3: BGP Routing Configuration

🛣️ Goal: Configure BGP and examine routing decisions

Connect to R1 FRR shell:
docker exec -it clab-frr01-R1 vtysh
Show BGP summary:
show ip bgp summary
Show BGP neighbors:
show ip bgp neighbors
Show routing table:
show ip route
Show BGP routes:
show ip bgp
Exit vtysh:
exit

BGP Path Selection Algorithm (in order):

1. Highest Weight (Cisco-specific, local to router)
2. Highest Local Preference (within AS)
3. Locally originated routes
4. Shortest AS Path
5. Lowest Origin (IGP < EGP < Incomplete)
6. Lowest MED (Multi-Exit Discriminator)
7. eBGP > iBGP
8. Lowest IGP metric to next hop
9. Oldest route
10. Lowest Router ID

Interview Question: What's the difference between BGP and OSPF?
Answer: BGP is path-vector, used for inter-AS routing, focuses on policies. OSPF is link-state, used within AS, focuses on shortest path (Dijkstra).

5 Scenario 4: Network Troubleshooting

🔧 Goal: Systematic troubleshooting methodology

Problem: Can't reach a service

1. Test Layer 3 (IP) connectivity:
ping <destination_ip>
2. Check routing:
ip route get <destination_ip>
3. Trace the path:
traceroute <destination_ip>
4. Check if port is open:
nc -zv <destination_ip> <port>
5. Check firewall rules:
iptables -L -n

Hypothesis Tree:

• Network unreachable? → Check routes
• Ping works but service doesn't? → Check application
• Partial connectivity? → Check firewall/ACLs
• Slow response? → Check latency, packet loss, MTU

Problem: High latency

1. Measure latency with stats:
ping -c 100 <destination>
2. Check interface errors:
ip -s link show eth0
3. Check TCP retransmissions:
ss -ti | grep retrans

Common causes:

• Network congestion → Check link utilization
• Packet loss → Check error counters
• Path MTU issues → Test with different packet sizes
• Application slowness → Profile the app

🎤 Interview Talk-Tracks

Common Questions & 90-Second Answers

Q: Explain the TCP 3-way handshake

A: TCP uses a 3-way handshake to establish reliable connections. (1) Client sends SYN with initial sequence number. (2) Server responds with SYN-ACK containing its own sequence number and acknowledging client's. (3) Client sends ACK to confirm. This synchronizes sequence numbers for reliable, ordered data delivery. I've debugged issues where SYN packets were dropped by firewalls - you'd see retransmissions in tcpdump.

Q: How does BGP path selection work?

A: BGP uses a multi-step algorithm. Key factors in order: Weight (local), Local Preference (AS-wide), locally originated, AS Path length (shorter wins), Origin type, MED, eBGP over iBGP, IGP metric. In practice, you control outbound with Local Pref and inbound with AS Path prepending. I've used this to implement traffic engineering - prepending AS path to make routes less preferred.

Q: Troubleshoot: Users can't reach web server

A: I follow OSI layers systematically. (1) Physical/Link: Check interface status with ip link. (2) Network: Test reachability with ping, check routing with ip route get. (3) Transport: Verify port is listening with ss -tuln, test connectivity with nc. (4) Application: Check service logs, test with curl -v. I'd also check firewalls, ACLs, and security groups.

Q: What's the difference between TCP and UDP?

A: TCP is connection-oriented, reliable (ACKs, retransmissions, ordering), with flow control and congestion control. Overhead from 3-way handshake and state tracking. UDP is connectionless, unreliable (no ACKs), lower overhead. Use TCP for data that must arrive correctly (HTTP, SSH). Use UDP for real-time/latency-sensitive apps where some loss is acceptable (VoIP, video streaming, DNS queries).
